## 0. 이번 라운드는 **실험**이다

유저 질문: *"조건이 완전히 같을 때도 오류가 생기는지."*

내 주장은 **「라운드마다 오류가 나온 건 명세가 불안정해서가 아니라, 매번 새 계측기를 붙였기 때문」** 이다.
3차는 tcx·오라클을 처음 썼고, 5차는 오라클을 **전면** 적용했다(실행 커버리지 1.5% → 약 50%).
그러니 그때마다 안 보이던 게 보였다. 이 주장이 맞는지 **이번에 가른다.**

### 조건을 맞췄다
- 5차 정정 **22곳 반영 완료**(`_spec/patch5.py`) — 너희가 5차 결과를 다시 찾을 일은 없다
- 5차가 **따로따로 발명한 계측기 4개를 전부 등재**했다 → `_verify3\TEMPLATE.rs` 의 **ⓐ~ⓕ**
  (5차엔 `offset_of!` 는 A 만, `derive(Debug)` 관통은 D 만, 바이트 diff 는 C 만, 독립 재구현은 B 만 썼다)
- 게이트에 **G11**(`history` 가 지시한 ev 상향이 표에 반영됐나)이 추가됐다

### ★모든 발견에 `found_by` 를 붙여라 — 이게 실험의 전부다
| 값 | 뜻 |
|---|---|
| `reused` | **내가 5차에 이미 쓰던 기법**으로 찾았다 |
| `inherited` | 5차에 **다른 배치가 발명한 기법**(ⓐ~ⓕ)을 이번에 처음 써서 찾았다 |
| `new` | 이번에 **내가 새로 만든 기법**으로 찾았다 |

**미리 박는 예측**(반증 가능하게):
- `reused` 실오류가 **≈ 0** 이면 → 내 주장이 맞다. 명세는 안정적이고, 발견은 계측기가 만든 것이었다.
- `reused` 실오류가 **여러 건**이면 → 내 주장이 틀렸다. 명세가 진짜 불안정하다는 뜻이고,
  그러면 **라운드를 더 도는 게 답이 아니라** 명세 구조를 바꿔야 한다.
- `inherited` 는 몇 건 나와도 정상이다 — **계측기 확산**이지 명세 문제가 아니다.

정직하게 붙여라. 애매하면 `reused` 쪽으로 적어라(내 주장에 불리한 쪽). 이 실험은 **내가 틀렸는지 보려고** 하는 것이다.

## 1. ★산출물 계약 — **이번부터 기계 판독 패치가 필수다**

5차에 `ev4→ev2` 상향 **492행 중 317행이 유실**됐다. 너희가 집계표로 보고했고 내가 행 목록을
요구하지 않았기 때문이다. **내 잘못이고, 그래서 계약을 만들었다.**

**`_verify6\<배치>\patch.json` 을 반드시 써라.** 산문 보고서(`<배치>6_REPORT.md`)는 그대로 쓰되,
**정정과 ev 상향은 이 파일에 구조로** 넣어야 반영된다.

```json
{ "round": 6, "batch": "A",
  "errors": [
    { "path": "/specs[0]/logic",
      "kind": "실오류",
      "old": "<정본에 실제로 있는 부분문자열 — 이걸로 찾아 바꾼다>",
      "new": "<대체 문자열>",
      "evidence": "오라클 A6_o3.tsv 26/26 · IR m04.ll:44245",
      "behavior_change": true,
      "found_by": "reused" }
  ],
  "ev_up": [
    { "path": "/specs[16]/mem[0]", "from": 4, "to": 3,
      "evidence": "offset_of! 일괄 대조 MISMATCH 0 (A6_o1.tsv)" }
  ],
  "brief_errors": [ "…" ] }
```

규칙:
- `path` 는 **v3 경로 그대로** 써라(`mem`/`consts`/`knobs`/`open`/`notes`/`history`/`logic`/`one_line`).
  v2 로 옮기는 건 `applypatch.py` 가 한다.
- `old` 는 **정본에 실제로 있는 문자열**이어야 한다. 없으면 적용이 **실패로 보고**된다(조용히 넘기지 않는다).
- ★**`mem`(오프셋)의 ev 상한은 `3` 이다.** `to: 2` 로 적어도 3 으로 깎인다.
  이유: `METHOD_MAP:190` 서열이 `런타임 > tcx > 오라클` 이고 `:192` 가 「오프셋은 tcx 가 정본」이라
  못 박는데 `ev` 축은 `2 오라클 < 3 tcx` 라 **두 문서가 반대**였다(5차 배치B 적발).
  해소 = **주장의 종류마다 강한 증거가 다르다** — 오프셋은 tcx, 동작·임계는 오라클.
  `offset_of!` 실행은 tcx 와 **같은 등급의 교차검증**이라 등급이 아니라 근거를 보강한다.
  `consts`·`knobs`(임계·동작)는 `ev2` 로 올라갈 수 있다.
- ev 는 **숫자를 직접 박지 않는다.** `applypatch` 가 그 행의 설명란에 근거 문장을 붙이면
  `mkspec3.evtier` 가 거기서 등급을 **파생**한다. (`history` 에 "ev 4→2 하라"를 적어두고 표는
  안 따라간 5차 사고가 그래서 났다 — 지금은 G11 이 잡는다.)

검증: 제출 전에 `python -X utf8 applypatch.py 6 --only <배치> --dry` 를 돌려
**적용 실패 0** 을 확인해라. `--dry` 는 파일을 쓰지 않는다.

## 3. 판정 어휘 4종 — 특히 두 가지를 조심해라

`미탐색`(아직 안 읽음) / `재료 부재`(실체 없음, **범위 열거 필수**) / `표기 불가`(동작은 확정) /
`사실 서술`(물음이 아니다 → `notes[]`)

- ⚠**범위 한정된 「불가」는 재료 부재가 아니다.** "이 함수만으론 확정 불가"는 **호출부·생성부를 안 본 것**이다.
  5차 직전에 이 오분류 3건을 고쳤다. **미탐색을 불가로 적는 것이 이 파이프라인 최악의 오염**이다.
- ⚠**`notes[]` 는 파지 마라. 틀렸다고 보면 반증하라.** 5차 배치B 가 이 둘이 충돌한다고 지적했는데,
  구분은 이렇다 — **파기**는 "모르니 조사한다", **반증**은 "확정됐다는데 정말인가"다.
  후자는 **그 확정 근거를 겨냥**하면 된다(전수 재탐색이 아니다).
