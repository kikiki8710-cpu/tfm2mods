## §4 ★적발을 내가 직접 반증한 기록 — **오탐 19건을 걸러냈다**

도시에 §1-3 의 지시대로, 통합판 초판이 낸 적발을 IR 원문으로 전수 대조했다.
**초판은 도시에가 준 오프코드 매핑(`icmp`→임계 / `gep`→인덱스 / `phi·select·store`→태그 / `call`→인자상수)을 그대로 구현한 「분류식」**이었다.

### 반증 ① — `gep`→인덱스 매핑이 틀렸다 (**강한 적발 7건 전부 오탐**)

불투명 포인터 시대의 LLVM 은 구조체 필드 접근을 **전부** `getelementptr i8, ptr %p, i64 <바이트>` 로
정규화한다. 그래서 GEP 의 인덱스는 **배열 첨자가 아니라 바이트 오프셋**이고, 값의 종류를 전혀 말하지 않는다.

| 행 | 초판이 인용한 GEP | 실제 정체 | 같은 값의 진짜 자리 |
|---|---|---|---|
| `02 c4`(16) `태그` | `m12.ll:34916 getelementptr inbounds nuw i8, ptr %30, i64 16` | 구조체 **+0x10** | `m12.ll:34973 %68 = phi i64 [ 5,%49 ],[ 2,%61 ],[ 16,%55 ]` = SubPlan::AttackNexus 태그 |
| `05 c9`(8) | `m13.ll:29001 … i64 8` | **+0x8** | `m13.ll:29150 select i8 8, i8 9` |
| `13 c10`(8) | `m10.ll:11644 … i64 8` | **+0x8** | `m10.ll:11679 select i64 8, i64 12` |
| `14 c7`(16) | `m08.ll:94865 … i64 16` | **+0x10** | `m08.ll:94816 select i64 2, i64 16` |
| `19 c1`(1)·`19 c2`(3) `태그` | `m04.ll:62594/62598 … i64 1 / i64 3` | `jungle_camps` **i8 배열의 바이트 오프셋** | `store i8 1` / `store i8 3` = JungleType 판별자 |
| `11 c14`(8) | `m13.ll:12257 … i64 8` | **+0x8** | `m13.ll:12356 switch 케이스 `i8 8`` |

⟹ **GEP 는 기각 근거에서 뺐다. 구제에만 쓴다.**

### 반증 ② — `phi·select·store`→태그 매핑이 틀렸다 (**7건 오분류**)

`store`/`phi`/`select` 는 「값을 **산출**한다」만 말한다. **태그와 산출값을 가르지 못한다** —
가르려면 목적지 슬롯이 열거형 판별자인지 알아야 하고 그건 IR 오프코드가 아니라 `tcx`/`dienum` 의 영역이다.
초판은 그 매핑 때문에 `15 c0`(BattlePlanGoal::TryKill) · `17 c1`(Chat::Battle 3) ·
`18 c2~c6`(MainObjective::Repair 7 · Chat::Repair 23 · SerpenSetup 25 · Press 21 · PressChange 22)
— **전부 STORE 로만 관측되는 정상 태그 행 7건**을 「어휘결손(산출값)」으로 올렸다.

⟹ `태그`·`센티널` 의 지지 관측에 `STORE/PHI/SELECT/RET` 를 **포함**시켰다(어휘결손 71 → 53).

### 반증 ③ — 등급 강등 5건 (기각하지 않고 `약` 으로 내렸다)

| 위험 | 왜 | 해당 행 |
|---|---|---|
| **값 0 의 정규화** | LLVM 은 부호없는 `x > 0` 을 **`icmp ne x, 0` 으로 정규화**한다 ⟹ 0 에 대한 동등비교는 `임계` 주장을 **반증하지 못한다** | `01 c10` · `02 c3` · `07 c6` |
| **접힌 문턱** | 문턱이 `shl`/`mul` 로 접히면 리터럴은 **계수 쪽에만** 남는다 — 명세 자신이 `03 c5`(tps*2 의 `shl …,1`) · `09 c0` · `09 c5` 에 그렇게 적어 뒀다 | `03 c5` · `05 c2` |

### ★★그리고 판정식 자체를 뒤집었다 — 이게 이 라운드의 핵심

도시에 §1 의 경고(「후보를 늘리는 것이 곧 오탐을 늘린다」)는 **분류식의 성질**이었다.
그래서 판정식을 **분류에서 반증으로** 바꿨다:

> **분류식**: 관측을 kind 로 환산해 대조 → 「후보가 있는데 주장이 없으면 불일치」 → **관측이 늘면 오탐이 는다**
> **반증식**: 「그 주장을 **지지**하는 관측이 **하나도 없을 때만** 불일치」 → **관측이 늘면 오탐이 준다**

우연히 겹친 리터럴(GEP 바이트 오프셋, 작은 정수 겸용)은 반증식에서 **구제로만 작용**한다.
「귀속·추론은 구제에만」이라는 규칙이 **판정식 수준에서 강제**된다.

### 반증 ④ — ★**내가 낸 패치를 내가 반증하고 물렸다** (26행)

7차 배치C 의 `C_kind_proposal.json` 37행이 `/specs[i]/consts[j]/kind` 경로라 **원천 적용 불가**인 채
남아 있었다. 나는 그것을 `meaning` 패치로 번역해 **49행짜리 패치를 한 번 완성했다**(`--dry` 49/49 성공).
그런데 적용 후 상태를 시뮬레이션(`_after.py`)했더니 —

| | 강 | NEG | 어휘결손 |
|---|---|---|---|
| 패치 전 | 16 | 4 | 53 |
| **49행 패치 후** | **28** (증가) | 2 | 20 |
| **23행 패치 후**(최종) | **4** (감소) | 2 | 46 |

26행(13·14 부시 ID)을 `임계 → 인덱스` 로 옮긴 것이 원인이었다. 그 26행은 `select` 로 **산출될 뿐**
이 함수 IR 이 그 값으로 **첨자를 때리는 자리가 0건**(GEP/MINMAX/ARITH 없음)이다.
⟹ `임계`(지지 0) → `인덱스`(지지 0) 는 진전이 아니라 **라벨 교체**다. **뺐다.**

## §5 ★어휘 확정 — **6종**(+판정보류 1)

### 근거: IR 이 실제로 구별할 수 있는 것과 없는 것

| 판단 | IR 이 증명하나 | 근거 |
|---|---|---|
| 「순서비교의 문턱인가」 | **예** | `icmp ult/slt/…` 는 오해의 여지가 없다 |
| 「이산 코드인가」 | **예** | `switch` 케이스 라벨 · `icmp eq/ne` |
| 「산술 상수인가」 | **예** | `mul/udiv/shl/add/sub/and` 피연산자 |
| 「첨자인가」 | **아니오** | GEP 인덱스 = 바이트 오프셋(반증 ①) |
| 「태그인가 산출값인가」 | **아니오** | `store/phi/select` 는 둘 다 산출이다(반증 ②) — 목적지 슬롯을 알아야 하고 그건 `tcx`/`dienum` 의 영역 |

### 확정 어휘

| `kind` | 뜻 | 지지 관측 | 정본 해당 수 |
|---|---|---|---|
| **임계** | 순서비교의 문턱 | `CMP_ORD` | 25 |
| **태그** | 판별자·코드값(비교되거나 기록되는 이산 코드) | `SWCASE`·`CMP_EQ`·`STORE`·`PHI`·`SELECT`·`RET` | 64 → 84 |
| **센티널** | 부재·무한 표지 | 값이 `-1`·`255`·`i64::MAX`·니치 기준 + 위 관측 | 9 |
| **인덱스** | 첨자·첨자 상한 | `MINMAX`(clamp)·`ARITH`(`1-team` 류 첨자 산출) ※`GEP` 는 구제만 | 5~6 |
| ★**계수** | 산술 상수 — 배수·나눗수·가감분·스케일·**비트마스크** | `ARITH`·`MINMAX` | **13** |
| ★**산출값** | 비교 없이 **분기별로 내보내는** 값 — 부시 ID·end_plan 코드·점수 계수표 | `PHI`·`SELECT`·`STORE`·`RET` 뿐 | **40** |
| (kind 아님) **판정보류** | 리터럴 접힘 / 콜리 안 / `#dbg_value` 뿐 | — | 10 |

**왜 4종이 아니라 6종인가 — 숫자로**

- `계수` 없이는 `08 c3`·`14 c5`(셀 크기 32000, `udiv` 2회뿐) · `00 c7`·`07 c0`·`09 c3`·`16 c4`(백분율 100) ·
  `08 c5`(초 단위 15) · `10 c0`(마스크 65534) 가 **전부 `임계` 로 떨어진다.** 명세 자신이 두 행에서
  「**계수**다(임계가 아니다)」라고 적어 놓고도 칸이 없어 못 옮긴 상태였다. → **13행**
- `산출값` 없이는 `13`·`14` 의 목표 부시 ID 26행, `05` 의 end_plan 코드 10행,
  `01` 의 EntityType별 계수표(`m05.ll:40043 %32 = phi i64 [ 0,%45 ],[ -10,%46 ],[ 80,%37 ],[ 200,%22 ]`)가
  갈 곳이 없다. → **40행**

**왜 7종·8종이 아닌가**

- `길이`(`05 c11~c13` = `"PassiveLine"` 11자 등 3행)는 **3행뿐**이고 IR 명령에 흔적이 없다
  (`m13.ll:28955 #dbg_value(i64 11, …, DW_OP_LLVM_fragment, 64, 64)` = `&str` 팻포인터의 길이 조각에만 남는다).
  ⟹ 전용 어휘를 세울 만한 모집단이 아니다. **`계수`(호출 인자 상수)로 흡수**한다.
- `인자상수`는 **kind 가 아니라 증거의 부재**다(콜리 안에서 무엇이 되는지 이 범위에선 안 보인다).
  ⟹ `판정보류` 라는 **상태**로 두고 kind 로 만들지 않는다.

## §7 ★`mkspec3.py` 파생 규칙 변경안 (메인이 적용 — 나는 MIG 루트를 고치지 않았다)

현행(`mkspec3.py:348-352`)은 `meaning` 낱말 → `kind` 단일 경로다. **세 군데를 바꾼다.**

### ① 파생의 1순위를 **IR 관측**으로 바꾸고 `meaning` 은 동률 해소로 내린다

```python
# _verify8/B/gate.py 의 observe() 를 그대로 쓴다(피연산자 슬롯 강제판).
obs    = observe(ir_file, ir_frm, ir_to, x.get("value"))
strong = {k: v for k, v in obs.items() if k not in ("CALLARG", "DBGSTR", "GEP")}
word   = word_kind(kmat)          # 현행 낱말 매칭 = 이제 **힌트**

if   not strong:                             kind = word or u"미상"   # 접힘·콜리 안 → 낱말 존중
elif word and word in SUPPORTED_BY(strong):  kind = word              # ★구제 우선
else:                                        kind = IR_KIND(strong)   # 낱말이 지지 못 받으면 관측이 정한다
```
우선순위 `IR_KIND` = `CMP_ORD→임계` > `SWCASE|CMP_EQ→(센티널값이면 센티널 else 태그)`
> `MINMAX→인덱스` > `ARITH→계수` > `PHI|SELECT|STORE|RET→산출값`.

⚠**`GEP` 를 어디에도 넣지 마라**(반증 ①). ⚠**`STORE/PHI/SELECT` 를 `태그` 로 매핑하지 마라**(반증 ②).

### ② 어휘를 6종으로 넓힌다
`{센티널, 인덱스, 임계, 태그}` → `{센티널, 인덱스, 임계, 태그, `계수`, `산출값`}` (+상태 `미상`).

### ③ 낱말 매칭에 **부정문 가드**를 넣는다
```python
NEG = re.compile(u"(?:값)?\s*(?:가|이|은|는|도)?\s*(?:아니다|아님|아니라|아니고)")
# 낱말 뒤 16자 안에 NEG 가 걸리면 그 낱말은 **매칭에서 제외**한다.
```
현행 `_EVTAIL` 절단은 **정형 꼬리만** 자른다(주석이 스스로 「이 절단만으로는 부족하다」고 적어 뒀다).
실제 오염은 정형 꼬리가 아니라 **본문의 부정문**이고, §3 의 4행이 그 전량이다.

### ④ (권장) 증거를 `meaning` 에서 분리한다
`mkspec3.py:74` 주석의 ①안. `apply_evup` 이 근거를 **본문에 덧붙이는** 한 같은 사고가 재발한다.
`consts[].evidence` 를 새 키로 빼면 `_EVTAIL` 정규식도 부정문 가드도 필요 없어진다.
⚠단 `ev` 파생(`evtier`)은 **두 필드를 합쳐서** 봐야 한다(지금은 합쳐진 문자열을 본다).

## §8 ★내 지시(도시에)의 오류 — 7건

`patch.json` 의 `brief_errors[]` 에 기계 판독 가능한 형태로도 실었다.

1. **§1 「임계 111행」이 틀렸다.** 정본 실측은 **107**행(태그 64·센티널 9·인덱스 6, 합 186).
2. **후보 3벌의 실측치 「26/40 · 72/186 · 6건」이 전부 실행값과 다르다.** 실행값 = **B 102/186 · C 68/186(+보류 20) · D 52/186**.
3. ★**오프코드 매핑 `phi·select·store`→태그 가 틀렸다.** 산출은 태그와 산출값을 못 가른다 — 그대로 쓰면 정상 태그 행 7건이 오적발된다(실제로 그랬다).
4. ★**오프코드 매핑 `gep`→인덱스 가 틀렸다.** 불투명 포인터 IR 에서 GEP 인덱스는 바이트 오프셋이다 — 그대로 쓰면 7건이 오적발된다(실제로 그랬다).
5. ★**§5 표의 `errors[].kind` 3종(`실오류`/`오탐`/`보강`)으로는 이 축의 주된 판정을 못 낸다.** 53행이 `표기 불가`다. 지시문은 「고칠 자리는 `meaning` 이거나 파생 규칙」이라고만 적고 **`meaning` 으로 갈 수 있는 곳이 현행 4종 안뿐**이라는 한계를 안 적었다.
6. ★★**`applypatch.py` 의 `already()` 가 `new[:80]` 부분문자열로 「이미 적용」을 판정한다** ⟹ **긴 `meaning` 의 꼬리만 고치는 정정은 조용히 버려진다.** 이 패치 초판의 `06 c0`·`07 c1`(이 라운드에서 가장 확실한 2건)이 실제로 그렇게 삼켜졌다(`정정 47/47 … (이미 적용 2)`). 이 도구의 존재 이유가 「조용한 no-op 금지」인데 그걸 이 함수가 뚫고 있다. **전체 문자열 동일성으로 고쳐야 한다.** 나는 머리쪽 문면도 같이 고쳐 우회했다.
7. ★**7차 배치C `C_kind_proposal.json` 37행에 대한 부분 반전**(§5-b 규칙 4 대로 오류 1건으로 셈). 그 제안은 적용 불가 경로라 방치돼 있었고, 전수 재검 결과 **11행은 확인·채택**, **26행(부시 ID `인덱스`)은 기각**했다(반증 ④).
   부수 지적: `dossierfresh.py` 가 `_gates\consts_kind\` 후보 3벌을 스탬프에 안 넣는다 — 이 라운드의 실질 입력인데 신선도 밖이다.
