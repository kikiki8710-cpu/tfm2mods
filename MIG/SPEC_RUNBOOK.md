# 1. 한 줄로 본 파이프라인

```
S0 표본 선정 ─→ S1 사전 미리 채우기 ─→ S2 독립 재작성 ×N라운드 ─→ S3 QC ─→ S4 교차대조
                                              ↑                              │
                                              └────── 수렴 안 하면 재투입 ─────┘
                                                                             ↓
      S7 병합·투영·저장 ←─ S6-b 기계 검증(tcx·오라클) ←─ S6 미확정 해소(재료 확장) ←─ S5 수렴 판정
```

**핵심 발상 하나만 기억하면 된다: "한 번 잘 읽기"가 아니라 "독립적으로 여러 번 읽고 어긋난 곳만 사람이 본다".**
IR 독해는 지어내기(hallucination)보다 **빠뜨리기**가 훨씬 많은데, 검사기는 지어낸 것만 잡는다. 빠뜨린 것은 **독립 2회 대조**로만 드러난다.

# 2. 왜 다회 재작성인가 — 실측 수렴 곡선

같은 20개 함수를 서로 안 보여주고 독립 재작성한 라운드 간 일치도(`speccmp.py`):

| 대조 | 판정상수 | 호출 | 구조체필드 | 의미 |
|---|---|---|---|---|
| **r1 ↔ r2** | 87.0% | 74.7% | 84.2% | 1차만 믿었으면 **판정상수 8개 중 1개가 틀렸을 것** |
| **r3 ↔ r4** | 96.6% | 96.2% | 95.7% | 사전 도구(`distruct`/`dienum`) 투입 후 |
| **r5 ↔ r6** | **100.0%** | 97.9% | 93.0% | 잔여 8개만 재투입 → **판정상수 완전 일치** |

읽는 법:
- **판정상수(constants)가 수렴의 주지표다.** 이게 100%면 "AI가 무엇을 기준으로 판단하는가"가 확정된 것이다.
- **`호출`과 `필드`의 잔여 불일치는 대부분 표기 차이**다. r5↔r6의 필드 93%는 사실 충돌이 아니라 한쪽이 중첩 구조체를 절대 오프셋으로, 다른 쪽이 상대 오프셋으로 적은 것이었다(전수 확인함).
- ⚠**일치는 하한이다.** 둘 다 같은 걸 놓치면 100%로 나온다. 그래서 S6(재료 확장)이 따로 필요하다.

**r1↔r2의 74.7%(호출)가 이 파이프라인의 존재 이유다.** 1회 독해를 정본으로 삼으면 안 된다.

# 3. 단계별 절차

## S0. 표본/대상 선정 — `pick20.py`

시범 배치라면 **대표성**이 전부다. 쉬운 것만 고르면 일정 추정이 통째로 틀어진다.

`pick20.py` 의 표본 규칙(그대로 재사용 가능):
- IR **100~500줄** 구간 — 함수 개수의 36.7%로 가장 대표적
- `game-ai\src\**` 소스만 (core/std 제네릭 인스턴스 제외)
- **클로저 제외** — 부모의 일부라 단독 명세 단위가 아니다
- **한 소스 파일당 최대 2개** — 몰리면 문맥이 공유돼 속도가 부풀려진다
- AI 판단 계층 위주 정렬(`plan_legacy` / `*_score` / `*_eval` / `fight_*`)

출력 = `spec_batch1.json`(함수명 · 소스 `파일:줄` · **IR 파일 + 본체 줄범위**).

⚠**`sym` 필드는 믿지 마라** — 메타데이터 id 가 들어간 버그가 있다. 심볼은 `ir_from` 줄의 `define` 에서 직접 읽어라.

**실전 대상 선정이라면** 표본 규칙 대신 목적으로 고른다: 바꾸고 싶은 행동 → 그 행동을 내는 플랜/술어 → 그 함수. 단 **"한 파일당 2개" 규칙만은 유지**하라(문맥 공유로 인한 착시 방지).

## S1. ★사전 미리 채우기 — 여기서 병목의 60~70%가 사라진다

작성 에이전트가 DWARF를 손으로 타게 두면 안 된다. **배치를 던지기 전에** 사전을 만들어 둔다.

| 도구 | 만드는 것 | 규모(실측) |
|---|---|---|
| ★**`tcxdict.py`** | 구조체·열거형 **정본 사전**(컴파일러 `tcx` 출처) | 게임 타입 **4,586** / 필드 15,138 / variant 13,294 |
| ~~`distruct.py`~~ | (2차 폴백) DWARF 역산 구조체 사전 — **키가 leaf 이름 1개뿐이라 동명끼리 덮어쓴다** | 26,416키 중 91.4%가 제네릭 인스턴스 |
| ~~`dienum.py`~~ | (2차 폴백) DWARF 역산 열거형 사전 — tcx 와 **모순 0**이나 커버리지 39.7% 결손 | 7,016 |
| `divtable.py` | `dyn Trait` vtable 슬롯 이름 | — |
| `fnparts.py` | 함수 본문 조각 위치(**본문 읽기 전에** 먼저) | `_gcbc` 자동 폴백 |
| `knobscan.py` | 매직 상수 전수 + 함수명 + `파일:줄` | 노브 후보 인벤토리 |
| `rmetadocs.py` | 개발자 한국어 주석 → `_docs\*.txt` | **2,925개 · 7초** |

★**두 개의 규칙만 지침에 박아두면 배치 품질이 확 오른다:**
1. **IR 을 읽기 전에 `MIG\_docs` 를 먼저 grep 하라.** 우리가 역추적하려던 코드표가 개발자 주석에 그대로 적혀 있는 경우가 많다.
2. **`_gaibc` 에 `declare` 만 있으면 `_gcbc`/`_gvbc` 에서 `define` 을 찾아라.** 1~6차에서 17건이 "본문 없음"으로 포기됐는데 전부 `_gcbc` 에 있었다.
3. ★**사전은 `tcxdict` 를 1차로 쓰라.** 구사전과 충돌하면 **`tcx` 가 정본**이다(컴파일러가 직접 말한다). 구사전은 **tcx 에 없을 때만** 2차 폴백으로. 근거·수치 = `IR_TOOLKIT.md §6-b`.

⚠**성능 사고 주의**: 사전 도구가 느리면 그 자체가 신호다. `dienum.py` 가 40분 걸린 원인은 정의만 해두고 안 쓴 정규식 대신 열거자마다 70MB 파일을 다시 `re.search` 한 것이었다. 파일당 1회 dict 로 바꿔 **40분 → 57초**. **자매 도구(`distruct` 58초)와의 시간 격차 자체가 버그 신호였다.**


「분류차」로 표시되는 것은 사실 차이가 아니라 양식 차이(구조체 오프셋을 `constants` 에도 적은 것)이니 무시한다.

## S5. 수렴 판정 — 언제 멈추나

**멈춤 조건: 판정상수(`constants`) 일치 100%.**
- 100% 미만이면 **불일치가 남은 함수만** 다음 라운드에 재투입한다(전량 재투입 금지 — 낭비다).
- 실제 진행: r1~r4는 20개 전량, **r5·r6은 잔여 8개만**. 그 8개에서 판정상수 100% 달성.
- `호출`/`필드`는 100%까지 갈 필요 없다. 잔여를 **표기 차이인지 사실 차이인지 눈으로 한 번 확인**하고 넘어간다(이번엔 전부 표기 차이였다).

## S6. ★미확정 해소 — 여기서 재료를 바꾼다

S5까지는 **정해진 IR 줄범위 안**만 읽는다. 그래서 `unknown` 이 쌓인다(20함수 기준 **157건**).
S6은 **범위와 재료를 넓히는 별도 배치**다. 이게 이번 작업에서 가장 수확이 컸다.

넓히는 축 4가지:
1. **aux 범위** — 담당 범위 밖의 클로저/헬퍼. `fnparts` 로 찾아 `aux: [{ir_file, ir_from, ir_to}]` 로 명시하고 읽는다
2. **다른 크레이트** — `_gcbc`(game_core 본문·정적 vtable 전역) / `_gvbc`(game_view = UI·렌더러)
3. **rmeta** — 개발자 주석(`_docs`), 식별자 테이블, (미탐색) MIR/Span
4. **아웃오브라인 본체** — 인라인돼 사라진 줄 알았던 함수의 `define` 이 따로 있는 경우(`fnparts`)

산출물 = **오버레이 JSON** (`resolved_<날짜>.json`): 함수별로 `resolved`(was/now 쌍) · `new_knobs` · `still_unknown`, 그리고 여러 함수가 공유하는 사실은 `_shared` 에 한 번만.

**실측 성과**: `unknown` **157 → 22**, `knobs` **99 → 208**, `resolved` **104건**.
그리고 **"원리적 불가" 판정이 7건 뒤집혔다** — 전부 원인이 같았다: **가진 재료의 한계를 문제의 한계로 착각.**

| 뒤집힌 판정 | 무엇으로 |
|---|---|
| game_core 함수 본문 9건 "별도 크레이트라 없음" | `_gcbc` |
| `Arc<dyn>` vtable 슬롯 8건 "정적 vtable 없음" | `_gcbc` 의 정적 vtable 전역 |
| `objective_entity_id_...` 의 `_ => None` "LLVM이 제거" | `fnparts` 로 아웃오브라인 본체 발견 |

## S6-b. ★검증 단계 — 오라클과 `tcx` (2026-09-11 신설)

S6 까지는 **읽어서 만든 표**다. 이제 그 표를 **기계로 검증하는 두 경로**가 생겼다.
전문 = `IR_TOOLKIT.md` **§6**(tcx 사전·감사) / **§7**(SDK 실행 오라클).

| 경로 | 무엇을 검증 | 한계 |
|---|---|---|
| **`tcxdict` / `tcxaudit`** | 구조체 오프셋·열거형 태그·필드 이름 = **컴파일러 정본** | ADT 아닌 것(vtable 슬롯), `&dyn` 팻포인터 뒤 절반 |
| **SDK 실행 오라클**(`-C lto=fat`) | `pub` 함수의 **입출력 진리표** | `pub` 인 것만. **외연이 같은 두 표현은 못 갈린다** |

**언제 쓰나**
- 명세에 오프셋을 하나라도 적었으면 → `python tcxaudit.py --prose <문서.md>` 를 **제출 전에** 돌려라.
  실측: 발표분 778건 감사에서 **오귀속 4건**이 나왔고 전부 산문 쪽이었다(구조화 표는 오귀속 0·밀림 0).
- 대상 함수가 `pub` 이면 → **진리표를 만들어 표를 대조**하라. `rule_scope` 13개에서 (A)~(E) **틀린 칸 0** 이 나왔고,
  덤으로 IR 로는 못 폈던 함수 6개가 **새로 완전 규정**됐다.

⚠**두 경로가 서로 어긋나면**: 구조/타입은 **`tcx` 가 정본**(컴파일러가 직접 말한다).
실행 결과가 IR 표와 어긋나면 **입력 구성과 IR 독해를 양쪽 다 의심**하라 — 오라클은 입력이 틀리면 **조용히** 틀린다.

# 4. 판정 어휘와 **범위** 규칙 (이게 제일 중요하다)

★**"X 불가능"이라고 쓰지 마라. "A 방식으로는 X 불가능, 미탐색 = B" 라고 써라.**
범위를 안 적으면 다음 세션이 **다른 방식조차 시도하지 않는다.** 이번에 7건이 그 함정이었다.

명세 JSON 의 `still_unknown` 항목은 이 셋 중 하나로 분류해서 쓴다:

| 분류 | 뜻 | 예 |
|---|---|---|
| **표기 불가** | 동작은 확정, 소스 표기만 불가 | `column:` 이 전 모듈 0이라 한 줄 안의 `A \|\| B` 순서 복원 불가 |
| **재료 부재** | 이 재료에 실체가 없음(탐색 범위를 열거) | `MF_SRC_NAMES` — IR 3종·rmeta 3종·전 rlib·exe 전량 0건 |
| **미탐색** | 불가가 아니라 아직 안 읽음 | `resolve_join_stake` 1,353줄 |

**세 번째를 첫 번째로 적는 것이 최악의 오염이다.** 다음 세션이 진짜로 포기한다.

확정된 재료 한계(현재까지):
- **`column:` 이 `_gaibc`/`_gcbc`/`_gvbc` 전 모듈 0건** — 같은 줄 안 표현식 순서는 **IR로는** 불가. ★단 **rmeta MIR/Span 은 미탐색**이라 원리적 불가가 아니다.
- **빈 match arm(`{}`)은 명령을 안 만들어 `!DILocation` 이 없다** — 줄 배정 불가(동작은 확정 가능)
- **의미가 동일한 표기는 정규화된다**(`==5` / `>=5` / `>4`) — 원본 표기 소멸

# 5. 함정 톱 10 (전부 이번에 실제로 밟았다)

1. ★**열거형 태그 ≠ variant 인덱스.** 니치 최적화로 밀린다(`SubPlan`=idx+2, `LineGankerPhase`=idx+6). **반드시 `dienum.py` 의 `DISCR_EXACT` 를 인용하라.**
2. ★**`!dbg` 가 없어 보여도 `inlinedAt` 루트까지 타라.** scope 만 보면 `line: 1` 이 나오지만 루트를 따라가면 진짜 줄이 나온다.
3. ★**`DW_OP_not` 개수로 극성을 읽지 마라.** 이중 이상 NOT 은 컴파일러 아티팩트(전 모듈 57건/12모듈, 개수가 3·5·6인 사례 5건). **극성은 분기 방향으로 확정.** 단일 NOT 은 논리 부정이 맞다.
4. **동명 다른 타입 / 사전의 동명 충돌.** 사전 확장 시 라이브러리 타입이 게임 타입을 덮어썼다(`LineType` Top/Mid/Bottom → EXIF 태그, `State` → zlib). **디렉터리 우선순위**로 막아라.
5. **`Vec<T>` descent 시 같은 크기의 다른 인스턴스를 집는다.** leaf+size 만으로 매칭하지 말고 타입명 정규화까지 하라.
6. **오프셋만으로 필드 스캔하면 다른 구조체가 딸려 온다.** `+0x108` = 2,339곳 → `--src battle.rs` 한정 45곳. ★`fieldcodes.py` 는 gep 레지스터를 **파일 전역**으로 매칭하는 오염이 있다 — 후속 정본은 **`fieldall2.py`**(함수 스코프 + gep 체인 누적).
7. **상수 스캔이 값을 놓친다.** 비상수 `phi` 로 들어오는 값은 안 잡힌다(`exit_sub` 의 6·7, `dive_abort_src` 의 1·11이 그랬다). **store 지점의 phi 까지 봐야 전수다.**
8. **주석은 stale 일 수 있다.** rmeta 주석이 IR 과 충돌하면 **IR 이 정본**. (실제 사례: `ff_battle_exit.__1` 은 주석대로면 `exit_sub` 인데 IR은 `entry_src`)
9. **"노브"라고 적기 전에 소비처를 확인하라.** `BattlePlanGoal.__1` 은 생성 14곳 전부 리터럴 60인데 **산술·비교 소비처 0건, `Debug::fmt` 만 읽는다** — 노브가 아니다. `mf_swap.__0` 도 load 0건 = 순수 텔레메트리.
10. ⚠**성능/동시성 사고.** (a) 거대 `.ll`(60~75MB)에 줄 단위 `sed -n "${k}p"` 루프 금지 — 1시간 낭비 후 강제종료했다. 파이썬 통째 읽기 또는 `awk` 단일 패스. (b) **같은 산출물을 쓰는 배치를 두 번 띄우지 마라** — `dienum.json` 이 경합으로 덮어써진 사고가 **두 번** 났다. 새 배치 전에 이전 배치가 살아있는지 먼저 확인하라.
